# Output contract

The contract describes what the agent must deliver at the end of every creative turn and how Motion Studio checks it. The text the agent reads lives in each project's `.studio/context.md` (generated by `packages/core/src/project-template.ts`) and, in short, in the turn prompt (`packages/core/src/creatives/prompt.ts`); the checks are in `packages/core/src/creatives/composition-contract.ts` and `composition-turn.ts`, the schemas in `packages/shared/src/composition/` and `packages/shared/src/creative.ts`.

## Version 2: compositions (current)

Since phase 10 the agent **never renders final media and never installs renderers**. It delivers one **composition folder** per target format; Motion Studio validates it, shows storyboards and a live preview, and renders the final file on demand (an export that needs it, or the agent's `render_version`; decision 974 removed the Render button).

```
<project>/creatives/<date-title>/
  work/                                the agent's workspace
  outputs/vN/
    compositions/<preset-id>/          one per target format, written by the agent
      composition.json                 schema motion-studio/composition@1
      assets/…                         every file it uses (copies)
      layers/*.html                    optional html layers
    manifest.json                      schemaVersion 2, written by Motion Studio only
    <preset-id>.<ext>                  a render, only after Render (Motion Studio)
<project>/.studio/composition.schema.json   the full JSON Schema (about 27 KB), rewritten before every turn
<project>/.studio/cache/storyboards/<creative>/vN/<preset-id>/   storyboard frames (Motion Studio, regenerable)
```

- The prompt carries a short summary of the schema and a valid example; `.studio/context.md` has the layer contract (`msReady`, `msSeek`/`msTimeline`, `msParams`; no network, Worker, AudioContext or autoplay), the font rules (local files in `assets/`, declared in `fonts[]`, loaded with `FontFace`) and examples of the common cases. The full JSON Schema is the file in `.studio/`, not inlined.
- The machine block of the prompt has `contract: 2`, `schema` and, per format, `compositionDir` (and `maxDurationSec`). There is no `renderCommand` and no encoding guidance any more.
- **Anything else the agent writes in `outputs/vN/`** (media files, a `manifest.json`, compositions of formats that are not targets) is removed after the turn, and the chat says so.

### Checks (problems)

After every attempt each target's folder is checked; each problem reads `compositions/<id>: <text>` and goes to the fix loop.

| Situation | Problem |
|---|---|
| No folder, or no `composition.json` | `Missing composition for <label> (<id>): write compositions/<id>/composition.json` |
| A symlink, a hard link, a special file, over the limits | `The composition folder cannot be read safely (<path>)…` |
| Two file names equal after Unicode NFC | `Two files of the composition folder have the same name once Unicode-normalised…` |
| `composition.json` not UTF-8 JSON, schema or semantic errors | the `composition.*` messages of `validateComposition` (after `normalizeComposition`) |
| A video whose duration is far from the brief's (more than the greater of 1 s and 10%) | `The composition lasts <d>s, but about <t>s were requested…` |

**Warnings** never block: the static checks of every `layers/*.html` (`staticLayerCheck`: network, workers, audio, autoplay) and the validator's warnings (e.g. a still's ignored animations). They are returned by `validate_composition` and summarised in the chat after the turn.

After the agent is gone the core rewrites `composition.json` in its normalised form (when that differs; the agent's original is kept in `.studio/cache/agent-originals/<creative>/v<N>/<format>.json`), then hashes the folder itself (`compositionHash`); nothing the agent writes is trusted for the hash. Up to 3 attempts, as before.

### What Motion Studio records

- `versions.json`: `compositions[]` (`format`, `dir`, `hash`, `problems`, `followsFormat` on followers), `outputs` only for renders (none right after a turn, except carried renders), `tools: []`, `renderCommand: null`.
- `manifest.json` v2: `{ schemaVersion: 2, compositions, renders }`; v1 manifests of older versions stay readable.
- Storyboards: after the version is saved, one 270 px JPEG per scene start plus the poster at 1 s (a still: one frame), with a `storyboard.json` index carrying the composition hash; made again on request when missing or stale.

### Targeted turns, carried formats and followers

The phase 9 rules apply to composition folders:

- **Carried primaries.** A primary not targeted is carried when the base version has its own composition entry and the folder, hashed before the agent starts, still has the recorded hash (else it becomes a target). Every file is copied with `COPYFILE_EXCL` and verified against the sha256 read then; the copy must hash to the recorded hash. It keeps its recorded problems. A legacy base (no compositions) carries nothing: every primary is a target.
- **Followers.** A follower's entry is its primary's composition (`dir` and `hash` of the primary, `followsFormat`, the primary's problems); no files are copied for it, and the render job copies the primary's render to it. Links added after a version was made apply from the next version. The link is checked with `canFollow` on the composition's duration; a link that no longer holds is removed with a chat message.
- **Renders carried.** When a format's composition is identical to the base's and the base render is current, the render (and its poster) is copied too, sha-verified.
- **Formats added without the agent.** On a v2 base the version gets the followers' entries and no agent runs. On a legacy base (decision 171), a turn without a message that only adds linked followers keeps the phase 9 path: the followers are copies of their primaries' files and the version stays a version 1 (media) one. Any other turn on a legacy base (a non-linked format added, a regenerate, a change request) is a conversion (below); the brief editor shows a notice before "Save and regenerate". If a primary's file can no longer be carried (changed or missing), the follower-only turn converts too.
- **History** (`formatHistory`) compares composition hashes for v2 versions and file hashes for legacy ones; a legacy version next to a v2 one always counts as changed.

### Pin frames and storyboard images

- The feedback frame of a pinned comment goes to `.studio/cache/pin-frames/<creative>/v<n>/<n>-<i>.jpg`. The agent reads it there and can never write there. The core writes it through real folders only (a link anywhere on the way means no frame) and a fresh `wx` temp file renamed into place. A version without a current render gets its frame from the composition.
- Storyboard images are served only through **signed, short-lived URLs**. The token-gated `GET …/versions/:n/storyboards/:format` returns:
  - each frame's `url`: `…/storyboard-files/<n>/<format>/<hash16>/f-<i>.jpg?s=<expiry>.<hmac>`, an HMAC-SHA256 bound to the exact path and keyed by a per-process secret, valid about 10 minutes;
  - `expiresAt`: the UI asks again before then.

  A missing, wrong or expired signature is refused (403). The path carries the composition hash, so new content never reuses a URL. Every confined file response is `Cross-Origin-Resource-Policy: same-origin`.

### MCP tools

- `validate_composition({ format? })`: the same checks on the current version (all target formats, or one); returns `formats[]` (`format`, `ok`, `hash`: the hash after Motion Studio normalises `composition.json`, the one the version records), `problems` and `warnings`. Saves nothing.
- `preview_frames({ format, times })`: 1–6 times in seconds; the core renders those frames (normalised media, at most 540 px wide) and returns them as PNG images (MCP image content) plus their times and any runtime errors. At most 10 calls per turn (`429` after that; malformed calls are refused without counting). Frames run in the preview lane (2 at a time, a short queue, a time limit each), never behind a long render.
- `validate_output` (version 1) no longer exists.

### Rendering

Only Motion Studio renders, outside the agent's sandbox, on request: an export that needs it, the agent's `render_version`, or the API (`POST …/versions/:n/render` with `formats`, or none for every primary). Since decision 974 the UI has no Render button.

- The render job has its own queue lane (one at a time) and never blocks agent turns. Storyboards and `preview_frames` use the preview lane.
- The engine is the desktop app's own Chromium (hidden, isolated Electron windows), or in the CLI system Chrome (Google Chrome or Chromium, `CHROME_PATH` first), else a Chrome for Testing downloaded with consent into `<config>/chromium/`. The engine is reported by `GET /api/render-engine`.
- Outputs: `outputs/vN/<preset-id>.<ext>` for videos (H.264 yuv420p, the composition's fps, tagged BT.709 with limited range, with the phase 8 encoding targets; the container is `mp4` when the format lists it, else the first of `mov`, `m4v` it lists; `mp4` if it lists none), and `<preset-id>.<ext>` for stills (`png` when the format lists it, else the first of `jpg`, `jpeg`, `webp` it lists; `png` if it lists none). Rendering the same version again replaces its file; the renders of other versions are never touched. Stills need no ffmpeg. They are written to a temp file and renamed into place. A cancelled or failed render leaves no file and no temp file. Each render is recorded in `renders[]` and in the version's `outputs` with `sha256` and `fromComposition`.
- Every video clip is first normalised (H.264 CFR at the composition's fps, short GOP, no audio, capped size) into `.studio/cache/media/`; the preview and the render both use the normalised file, and the preview plays the clip's audio from the original asset.

### Older creatives (version 1)

A creative whose versions have v1 manifests keeps its media and its exports. At its next change the turn is a **conversion**: the agent rebuilds each legacy format as a composition and applies the request, looking at reference frames of the old media that the core extracts into the protected cache (`.studio`, readable, never writable by the agent), and the chat posts "Converting to the editable format · costs more tokens this once". In the per-format history a legacy version next to a v2 one always counts as changed.

*Verified live (phase 10a, 2026-10-12):*
- with Haiku, a new creative's turn wrote only compositions (no render, no installs, 0 approvals);
- Render ★ produced H.264 BT.709 mp4 files and a still image that decode without errors;
- a creative made by the phase 9 build converted at its next change.

Details: `docs/superpowers/notes/2026-10-12-phase10a-live-checks.md`.

### Export

Decision 974: with `background: true` the export is a job (kind `export`, its own lane; the request answers `{ job }` at once after the checks it can make, its refusals as before); the job's `export` field reports `stage` (`rendering`, `copying`, `done`), the percent of the render jobs it waits for, and at the end the files written, the skipped ones and the renders with problems left out; a cancel cancels the render jobs it started (never one another request started). `quality` (`standard`, `high`, `max`) and `resolution` (the short side: 480, 720, 1080, 1440, 2160) apply to video compositions: the version's own render is at the format size and `high` (recorded in `outputs[].render` and `renders[].render` with the encoder that ran; a render without it counts as `standard`); another profile is rendered for the export alone (`render-export:` jobs in the render lane, into a temp folder), never recorded in the version. Stills, identity and store pack formats have no profile.

A ★ whose v2 version has no current render (or whose render file is gone) is rendered first: `POST …/export` enqueues the render job of that version (or joins the active one), waits for it, then copies; the response lists what was rendered (`rendered`). `POST …/export/prepare` starts those renders at once and returns their jobs, so the UI can show their progress before the copy. A render that fails is `409 export-render-failed` and nothing is copied. Legacy versions export their media as before. In the per-format summary `starRender` is `rendered`, `notRendered` or `stale`; `starFileMissing` is only for legacy files (or a follower with no qualifying version).

### Direct edits (the editor, phase 10b)

The editor changes a composition without the agent. Saving (`POST …/creatives/:c/edits`) makes a **normal v2 version**:
- `manifest.json` v2;
- in `versions.json`, `origin: "editor"` (absent means `"agent"`), `request` = the summary of the edits ("Direct edits: Title text, font Schibsted Grotesk and 2 more"), `basedOn` = the version edited, no `usage`;
- a `version` chat entry and a git commit.

Followers, carried primaries and carried renders follow the targeted-turn rules above. The composition goes through the same `validateComposition` (with the format) and `loadComposition` as an agent's (size, kind and the format's maximum duration stay hard rules), but NOT the check of the duration against the brief's: a direct edit's duration is the user's choice. The save records that choice on the format's entry (`userDuration: { durationSec, briefDurationSec }`, only when far from the brief). An agent turn that keeps that duration is not asked to bring it back to the brief, and its version carries the record on; this holds only while the brief still says `briefDurationSec`. An agent's own duration is never accepted this way, and a brief changed since the choice ends it. On top of those, the core refuses an editor save when:
- a `src` (of a clip or a font) is neither a file of the base version under `assets/` nor a file staged for this draft in the same preview session;
- an `html` clip's `src` changes, or an `html` clip is added;
- the `layers/` files are not byte-identical to the base's;
- a turn or a render of the creative is queued or running (`409 editor-busy`);
- the edited format's latest composition is no longer the draft's base (`409 editor-base-changed`; the draft is kept).

**`assets/lib/` is reserved for files the editor adds:** library assets and brand font files picked in the editor.
- They are named `assets/lib/<first 8 hex of the sha256>-<name>`.
- While the draft is open they live in the preview session's staging folder, `.studio/cache/editor-staging/<creative>/<id>/assets/lib/`. The composition server serves a session's `assets/lib/…` path from there only when the composition folder has no such file (the version always wins).
- At save, only the staged files the composition uses are copied into the new version, verified.
- An agent that edits such a composition keeps these files and their names. It should put its own files elsewhere under `assets/`: the prompt and `.studio/context.md` say so, but no check enforces it. A staged name that a version holds with other content is refused at save (`409 editor-staged-collision`).

**The next agent turn after a direct edit.** It builds on the editor version, never on what the agent remembers:
- At save, the core copies each own composition of the new version, byte for byte and verified, to `creatives/<slug>/work/editor/<format>/`, and the copy is in the version's commit (a restart from that version finds it). Before every agent turn the core aligns `work/editor/` with the base: an editor base gets its copies (an identical copy is kept), any other base leaves no `work/editor/`.
- The iteration prompt has a section "Direct edits by the user": `vN contains direct edits by the user: <summary>. Build on vN; keep those edits unless the user asks to change them.` (the summaries of consecutive editor versions in the base's line, oldest first, on one line), that `work/editor/<format-id>/` is the current source of those formats (an exact copy of `outputs/vN/compositions/<format-id>/`; any other copy elsewhere in `work/` is superseded), that generators and scripts in `work/` predate the edits (rerun one only reapplying them, or edit the composition directly), and to keep the user's values and the `assets/lib/` files.
- A duration far from the brief that the base keeps by the user's choice adds "Keep the current duration (…) unless the user explicitly asks for another one".
- The session is resumed as before (the agent's last session): the prompt section tells it explicitly what changed.

**User flags on clips and tracks.** They are optional, and the agent leaves them as they are (the schema's descriptions say so):
- `hidden` on a clip: it is not drawn, and an audio clip is not heard;
- `hidden` on a track: its clips are neither drawn nor heard;
- `muted` on a track: its audio is silent;
- `locked`: the editor refuses edits of that clip or track; scene operations still carry a locked clip with its scene.

**Comments (pins).** A pin may also carry:
- `clipId` (up to 64 characters) and `clipName` (up to 200; the name when the comment was made), neither with control characters, newlines or the Unicode line/paragraph separators;
- `range: { start, end }`, in seconds, `0 ≤ start < end`.

Older pins without them are read as before. The prompt line is `- <format> @ <t>s, point (x%, y%)[, clip "<id>" "<name>"][, range <a>–<b>s]: <note>`; id and name are JSON string literals (quotes, backslashes and any control character escaped). A range comment has two frames in the pin-frame cache: `<n>-<i>.jpg` at its start and `<n>-<i>e.jpg` at its end.

*Verified live (phase 10b, 2026-10-13):*
- editor saves made versions with `origin: editor` and no agent run;
- a staged upload and a brand font ended up under `assets/lib/`;
- Haiku received the clip and range lines above and edited that clip.

Details: `docs/superpowers/notes/2026-10-13-phase10b-live-checks.md`.

## Version 1: rendered media (legacy)

Versions made before phase 10 followed this contract. They stay readable, exportable and comparable; the next change turn on such a creative becomes a conversion to compositions. The text below describes how those versions were made.

The contract describes what the agent must deliver at the end of every creative turn and how Motion Studio checks it. The text the agent reads lives in each project's `.studio/context.md` (generated by `packages/core/src/project-template.ts`); the check is in `packages/core/src/creatives/output-contract.ts`, the manifest schema in `packages/shared/src/creative.ts`.

### Folder structure

```
<project>/creatives/<date-title>/
  work/                 the agent's workspace: sources, scripts, local dependencies
  outputs/v1/           delivery of version 1
    <preset-id>.<ext>   one file for each requested format
    manifest.json
    .previews/          posters of videos, generated by Motion Studio (do not write here)
  outputs/v2/ ...
```

Every turn writes into a new `outputs/vN/` folder (the exact folder is given in the request to the agent). Files are named `<preset-id>.<extension>`, for example `instagram-reel-9x16.mp4`; ids come from the workspace's format catalog (`.studio/presets/formats.json`, editable from the interface).

### manifest.json

```json
{
  "schemaVersion": 1,
  "files": [
    { "format": "instagram-reel-9x16", "file": "instagram-reel-9x16.mp4", "width": 1080, "height": 1920, "durationSec": 15 },
    { "format": "instagram-image-1x1", "file": "instagram-image-1x1.png", "width": 1080, "height": 1080 }
  ],
  "tools": ["remotion"],
  "renderCommand": "npx remotion render Main ../outputs/v1/instagram-reel-9x16.mp4"
}
```

- `schemaVersion`: always `1`.
- `files[]`: `format` (preset id), `file` (name only, no subfolders or `/` or `\`; `.` and `..` not allowed), `width` and `height` (positive integers), `durationSec` (positive number, optional: videos only).
- `tools`: list of strings, empty by default.
- `renderCommand`: optional; the command to run in `work/` to regenerate the outputs. It is quoted on one line (no control characters, at most 300 characters) when formats are added.
- `followsFormat`: optional, **written only by Motion Studio** on the entry of a linked format (see below): the file is a byte copy of that primary format's file. A `followsFormat` (or any hash) the agent writes is ignored and dropped.

The agent lists only the formats it was asked for. When a version also has carried or linked formats, Motion Studio rewrites `manifest.json` after the agent with every file of the version. Otherwise a corrupt manifest is never rewritten by Motion Studio.

### Targeted turns, carried and linked formats

A turn may apply to some formats only (`formats` in the turn request, the composer's "Applies to"). Motion Studio normalizes the list: formats not in the brief are dropped (a list with none in the brief is refused: 400 `formats-not-in-brief`), a linked format stands for its primary ("TikTok follows the Reel: the change applies to both"), and an empty or missing list means every primary format.

- **Targets.** The agent receives only the target formats (in "Required formats" and in the machine block) and is told that Motion Studio keeps the other formats unchanged and writes their files itself. A primary format with no usable file in the base version (missing, a symlink or a hard link) is always a target: it cannot be carried. A Generate with no message after formats were added to the brief targets only the added primary formats.
- **Carried formats.** After the agent's last attempt, the other primary formats are copied unchanged from the base version (the one restarted from, else the latest) into `outputs/vN/`, under the same file name, so the format's history does not grow. Each copy must match a trusted sha256 taken **before the agent starts**: the hash recorded for the base version, checked against the file at that moment (old versions without one are hashed then). A base file that is already not the recorded one is not carried: the format becomes a target. The source's current bytes are never trusted after the turn: a copy that does not match is removed and the version gets a problem ("… the file of vK is not the one recorded for that version…", or "Motion Studio could not put its file in this version"); the format is left out of that version. A carried file is checked only for presence and dimensions, and it keeps the `problems` it had in the base (old versions without per-file problems: only the version's problems that name its file, id or label), which count for the version's status; they are never sent to the agent.
- **Earlier versions are read-only.** Every existing `outputs/v*` folder of the creative except the new one is protected for the turn (sandbox `denyWrite` and the Edit/Write deny rules, plain and real path), the prompt says never to write there, and the render-command hint points at the new folder. Output folders are not versioned in git (`outputs/` is in the project's `.gitignore`), so the core also fingerprints those folders before the agent runs and, if anything changed, the chat shows a warning listing the paths.
- **Leftover processes.** When an attempt ends, the agent's whole process group is killed (SIGKILL), so nothing it left running writes in the folder while the core completes, validates and hashes it. On Windows there are no process groups: the core runs a tree kill (`taskkill /PID <pid> /T /F`) only while the agent process is still alive; descendants that outlive it are orphaned and cannot be reached, so this protection is best effort there. Each file the core copied is checked again against the version's recorded hash; a difference is a problem ("the file changed after Motion Studio copied it"), and a file that could not be hashed at all is a problem too ("could not be verified").
- **Core-owned names.** The carried files' names and `<follower>.<any extension>` belong to Motion Studio in that turn: a delivered file with such a name is a problem the agent receives in the fix loop ("… this name belongs to …; rename your file").
- **The agent wrote a non-target format anyway.** That is: after its last attempt the folder has an entry (file, link or folder) at the carried file's name, or its manifest lists the format. All such entries are removed first, before any copy (also when listed under another name, never a file a target delivered), then the carried file is put in its place, and the output gets the note `outputs.keptUnchanged` ("… was not part of this request: the agent's file was discarded and the previous one kept unchanged") — only when the core's copy really is there.
- **Linked formats (followers).** The brief's `links` (follower → primary) name formats that reuse a primary's file. The agent never makes them: after the carried files are in place, each link is checked again on the primary's real file (`canFollow` with its measured duration, an unknown duration being strict; the follower's maximum file size against the file's size), then the primary's file is copied to `<follower>.<primary's extension>` and verified by sha256. A follower's output gets a copy of its primary's `problems`. A follower whose copy fails is a version problem, never silently missing. Copies are never hard links (confined reads refuse files with more than one link).
- **A link that no longer holds** (e.g. a 70 s Reel and Shorts' 60 s limit) is removed from the brief and the chat explains it. When the primary was carried, this is known before the agent starts, so the agent makes the follower in the same turn. When the primary was just rendered, the follower is not delivered in this version (a version problem with the same text) and the next turn makes a dedicated version, since a primary format missing from the base is always a target.
- **Formats added without the agent.** When formats added to the brief are all linkable to primaries present in the base version (a brief save links each added format to the first primary it can follow, with the duration checked only at materialization), Generate creates `v(N+1)` without starting `claude`: the base's files are copied, the followers materialized, the manifest written, the version validated and committed. The version request reads "Added TikTok · Video 9:16 and YouTube · Shorts 9:16 using the Instagram · Story/Reel 9:16 (v5)" and the chat adds "· no agent needed". No usage is recorded: nothing ran, so the usage ledger has no row and the version has no `usage`. After a "Restart from here", such a version keeps the restart's intent: the next agent turn still forks the restored session. If any added format is not linkable, the agent runs for those only and the linkable ones are still materialized.

The final check of a version covers every file: targets with all the rules below, carried and linked files on presence and dimensions.

### Validation rules

After every attempt `validateOutputs` checks each target format of the turn (every format of the brief that the agent delivers); each output also records its own `problems`. The messages are the ones the agent receives (and that appear in the version as "problems"). They are written in the language set in **Settings → Language** at the time of the check; the English texts are shown here, and the Italian catalog has the same messages. Problems saved in a version are never translated afterwards.

| Situation | Message |
|---|---|
| Manifest missing | `manifest.json is missing in <folder>` |
| Manifest unreadable or not matching the schema | `Invalid manifest.json: <detail>` |
| Id not in the catalog | `Unknown preset: <id> (not in the format catalog)` |
| Format not in the manifest | `Missing format <channel> · <name> (<id>)` |
| Listed file missing or irregular (a symlink does not count) | `File not found for <id>: <file>` |
| Extension not allowed by the preset | `<file>: extension .<ext> not allowed for <id> (allowed: …)` |
| File over the preset's maximum size | `<file>: <x> MB, maximum <y> MB` |
| With ffmpeg/ffprobe: file unreadable | `<file>: cannot be read as media` |
| Resolution different from the preset | `<file>: resolution <w>×<h>, expected <W>×<H>` |
| Video with no detectable duration | `<file>: does not look like a video` |
| Duration over the preset's maximum | `<file>: duration <d>s exceeds the maximum of <m>s` |
| Duration far from the brief's (difference above the greater of 1 s and 10%) | `<file>: duration <d>s, about <t>s requested` |

With ffprobe available, width, height and duration are the measured ones (not the declared ones) and the output is "verified"; for videos a poster is also extracted into `.previews/<file>.jpg`. Without ffprobe the manifest values are used and the output is shown as "unverified". For images, duration is always ignored.

### Fix attempts

If there are problems, Motion Studio restarts the agent (in the same session) with the list of problems and asks it to deliver again in the same folder, updating the manifest. Only the target formats are checked and sent back: carried and linked formats never go to the agent for fixing. Attempts are at most 3 in total (the first turn plus two fixes). The exception is problems that are only unknown presets: the agent cannot solve them, so there is no retry. At the end the version is saved as **complete** (no problems) or **incomplete** (problems left, listed in the version), always with a git commit.

### MCP tool `validate_output`

In creative turns the agent can call `validate_output` (`studio` MCP server, no parameters) to run the same check on the current version before closing the turn; it returns `outputs` and `problems`, but saves nothing and does not count as an attempt. Outside creatives it answers "Validation is only available in creatives" (in the current language).

### Export

The outputs of a version are copied with **Export…** under the names `<slug>-<format>-vN.<ext>`, without overwriting and refusing folders inside the workspace. Files that cannot be exported are reported as skipped. See the README.
